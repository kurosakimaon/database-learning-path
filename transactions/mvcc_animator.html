提示：就快照读而言，RC 和 RR 的差别只有一件事 —— read view 建立的时机： RC 每条语句拍一次，RR 事务里第一次读拍一次、钉死用到头。（锁的范围两者也不同，RR 多的是 next-key lock，见页面底部第 ③ 条。）
可见性判断三问（顺着版本链从上往下，对每个版本问）：
① 是我自己写的吗？→ 可见（所以才读得到自己未提交的修改）；
② 写它的事务在我建立 read view 时提交完了吗？→ 可见；
③ 都没中 → 这个版本当它不存在，沿 undo 指针往下一个版本接着问。
第一个过了安检的版本，就是查询真正返回的那一行。 动画简化了什么 —— 四条边界，面试被追问就靠这些
① 真实 read view 里存的不是提交时间戳，而是 up_limit_id（建视图时最小活跃 trx_id）、 low_limit_id（下一个将分配的 trx_id）和当时仍活跃的事务 id 列表； 判断靠 trx_id 比大小，不靠「几点提交」。本动画用提交时钟是为了让快照能一眼看懂， 结论一样，但别说成「InnoDB 记录提交时间」——它记的是事务 id 的活跃集合。
② 只有快照读（普通 SELECT）才走版本链。SELECT ... FOR UPDATE、 ... LOCK IN SHARE MODE 以及 UPDATE / DELETE / INSERT 都是当前读：直接读最新版本并加锁。
③ 所以 RR 防幻读靠的不是 MVCC，是 next-key lock（记录锁 + 间隙锁）。RC 没有间隙锁， 同一条 UPDATE ... WHERE 在两个级别下锁的范围完全不同 —— 方向别记反：间隙锁锁住的是"还没有行的那段空隙"，所以范围扫描 + 并发 INSERT 在 RR 下最容易互相咬住，线上死锁日志里的高频主角是 RR 的间隙锁； 把级别降到 RC（锁范围只剩命中的记录）恰恰是常见的减死锁手段，不是加死锁的理由。
④ 版本链不是永远留着的：只有没有任何 read view 还可能需要它时，purge 线程才能回收旧版本。 一个忘了提交的长事务会把整条链钉在原地 —— undo 膨胀、链变长、后来每个查询都多跳几跳。 这就是「线上别留长事务、别开 START TRANSACTION 不提交」最直接的机理。 顺带一句：同一事务里混用快照读和当前读，「可重复」就破了 —— 当前读会返回你上次快照读里 根本不存在的新行，所以 MySQL 的 RR 不等于教科书里的 SERIALIZABLE。
