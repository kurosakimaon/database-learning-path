# 第 5 关：结丹期 · 查询内幕

老师傅带你钻进数据库的"大脑"看查询怎么跑

## 一、模块简介

徒弟啊，上一关你亲手造了页、B+ 树、Buffer Pool，
知道了数据库"怎么存"。
这一关师傅带你钻到另一半肚子里：
一条 SQL 进来，数据库"怎么想、怎么算、怎么跑、崩了怎么救"。

先记住一句话，这一关反复说，说到你烦为止：

> ◆ 查询优化器是个会计，不是预言家。
>   它不认"快不快"，只认估算的行数和代价公式。
>   统计信息一过期，它就能"正确地"选一个慢上百倍的计划。◆

这句话的意思，02_cost_model.cpp 用数字给你演得明明白白。

你是写 C++ 的，师傅给你几个翻译，本关所有示例都能对上号：

- **join 算法** ≈ 你写过的嵌套循环 / 双指针归并 / 哈希表查表，
  数据库里只是把这些算法搬到磁盘页上记账；
- **代价模型** ≈ 编译器里的"指令周期估算"——
  代价公式就是成本函数，选计划就是选最短路径；
- **EXPLAIN 计划** ≈ 编译器的 -S 输出——
  看汇编（执行计划）就能反推编译器（优化器）做了什么决定；
- **火山模型 next()** ≈ 迭代器 operator++()——
  拉一行是一行，控制流自上而下，数据流自下而上；
- **WAL 日志** ≈ 数据库的"提交前 journal"——
  先顺序追加写日志，再随机改数据页；
  崩了重放日志，没提交的就丢弃，就这么简单；
- **checkpoint** ≈ 把 WAL 里的"欠款"结清到数据页，
  然后 WAL 可以截断从头再来。

这一关的所有示例，要么用真 SQLite，要么用 C++ 手写迷你引擎，
没有一个是"看示意图"——每个数字都是实测的。

## 二、学习目标

学完本模块，你要能做到：

1. 手算四种 join 算法（块嵌 NL / Index NL / Sort-Merge / Hash Join）
   各自的页读次数和比较次数，说清楚"为什么数据库默认选 Hash"
   ——不是因为它比较次数少，是因为它的页读次数是 O(M+N)，
     而 Index NL 是 O(驱动行数 × 树高)——选择率高时差几百倍

2. 手写一个迷你代价模型（02_cost_model.cpp 就是模板）：
   代价 = 页读 × IO_COST(1.0) + 比较 × CPU_COST(0.005)
   知道 IO_COST 是 CPU_COST 的 200 倍（教学模型的简化比例；
   真实硬件上一页随机读可能相当于十万次比较，所以页读的真实权重只会更夸张）

3. 解释"统计过期为什么会让优化器选错计划"：
   选择率估 0.1% → est=50 行 → C 计划（索引+回表）估代价最低
   → 实际 99% → C 的真实代价 152710，是正确 A 计划（1072.5）的 142 倍
   —— 算账逻辑没错，料给错了（C 自己估 157、实际 152710，估错 973 倍）

4. 读懂 SQLite 的 EXPLAIN QUERY PLAN，看到每个关键字知道账本：
   SCAN（全表扫，页 = 表的页数）
   SEARCH USING INDEX（树上定位，页 ≈ 树高）
   COVERING INDEX（免回表，二级索引的叶子已经有你要的列）
   USE TEMP B-TREE FOR ORDER BY（filesort，排序落盘的代价）
   LIST SUBQUERY + BLOOM FILTER（IN 子查询物化）
   CO-ROUTINE（延迟关联——深分页改写的标志）
   AUTOMATIC COVERING INDEX（执行时临时建树——SQLite 的救场机制）

5. 说清"索引什么时候帮倒忙"：
   选择率 > 10%（经验阈值）时，回表的随机 I/O 比全表顺序扫贵；
   范围列右边的列全部失效（最左前缀的下半句）；
   LIKE 默认大小写不敏感 → 序对不上 → 不走索引；
   PRAGMA case_sensitive_like=ON 才能让 LIKE 走索引

6. 手推火山模型：一条查询的 next() 调用链怎么走，
   Hash Join 的 BUILD 阶段什么时候发生，
   LIMIT 10 为什么计划不变但执行只跑了 1/5000

7. 手写一个迷你 WAL（04_wal_and_crash.cpp 就是模板）：
   说清"提交 = WAL fsync 返回"这句话为什么是 WAL 的灵魂；
   恢复三规：有 COMMIT 记录 → REDO；无 COMMIT → 丢弃；
   校验和失败（torn write）→ 从这条往后全部不认；
   知道 NVMe 上随机写 ≈ 顺序写（实测 1.0 倍），
   真正的大头是每笔 fsync 往返（约 1ms），
   所以 WAL 省的是"随机→顺序"，group commit 省的是"fsync 凑车"

8. 知道 C++ 结构体对齐的坑能坑死 WAL 校验：
   WalRecord 字段净 36B，8 字节对齐 → sizeof=40，
   4 字节尾部 padding 排在 checksum 之后；
   如果用 sizeof - sizeof(checksum) 算覆盖范围，
   就把 checksum 自己算进去了——恢复时 100% 校验失败。
   正确写法：offsetof(WalRecord, checksum)

## 三、文件列表与学习重点

一共 7 个文件。4 个是主菜（C++ 3 个、SQL 1 个），
1 个 HTML 教具，tutorial.md 和 index.html 是地图。
顺序：先 join 算法（01）→ 代价模型（02）→ EXPLAIN 实练（03）
→ 火山流水线动画（explain_pipeline）→ WAL（04），
教具随时配合着看：

- **index.html** ← 本模块导航页（双击就能开）
  - 重点：先看它，知道每个文件干嘛的、按什么顺序啃

- **01_join_algorithms.cpp** ← 四种 join 算法真跑对比（★ 地基）
  - 重点：users 5000 × orders 50000（2% 悬空外键 = 1013 行）
    实测数字背下来（比较/页读是确定值；耗时随机器负载浮动，
    以量级为准——毫秒数每次跑会差 20~30%）：
    - BNL：2.5 亿比较 / 25000 页 / 122~133ms
    - Index NL：569893 比较 / 100147 页 / 2.2~2.3ms
    - Sort-Merge：947686 比较 / 108 页 / 1.79ms
    - Hash Join：55000 比较 / 196 页 / 0.30~0.31ms ← 完胜
  - 关键：matched = 48987（四算法一致），差 1013 = 悬空行数
  - 为什么 BNL 比 Index NL 慢 50 多倍？块嵌套循环把
    页读从 O(M×N) 压到 O(M+M×N/pagesM)，但比较仍是 O(M×N)
    ——2.5 亿次比较这一栏才是它的死刑判决。
    反过来 Index NL 页读账面更多（100147 > 25000）却快得多：
    那 50000 次主键探测全落在 Buffer Pool 里，账面页读≠磁盘页读。

- **02_cost_model.cpp** ← 迷你代价模型 + 统计过期翻车（★ 心脏）
  - 重点：代价 = 页读×1.0 + 比较×0.005（就这么朴素）
  - 三轮剧本：
    - 第一轮（STALE 0.1%）：优化器选 C，估代价 157.0 最低
    - 第二轮（真实 99%）：C 真实代价 152710，A 是 1072.5
      差了 142 倍——算账对，料错了（C 自己估 157、实际 152710）
    - 第三轮（ANALYZE 后）：优化器选 A，与上帝视角一致
  - 这三轮就是"ANALYZE 为什么重要"的完整证明

- **03_explain_drills.sql** ← 15 道 EXPLAIN 实战题（★ 实练）
  - 重点：users 5万 / orders 100万 / coupons 1000 + 4 个索引
  - 每道题：SQL → "你猜" → 真实输出（已注释写死）→ 解读
  - 实测数据：
    - amount>9800 → 19900 行（选择率 1.99%）
    - 杭州 → 6250 行；BETWEEN 100 AND 200 → 10100 行
    - orders 表 7733 页；idx_amount_status 3853 页；
      三棵索引树均 4 层
  - 关键计时实测：
    - LIMIT 10 早停：0.000043ms
    - 深分页 LIMIT 999990,10：0.012535ms
    - 改写 WHERE id>999990 LIMIT 10：0.000149ms（84 倍）
  - 末尾"四本账"总结：页账 / 序账 / 资格账 / 计划账

- **explain_pipeline.html** ← SQL 六道工序动画（★ 教具）
  - 重点：同一条 SQL（users JOIN orders WHERE amount>100）
    14 步走完：字符串 → token → 语法树 → 约束列表
    → 候选 A/C 打分 → 火山模型 BUILD/PROBE/EOF → 结果
  - 代价表（A=1072.5 vs C=152710）与 02 同源可直接对照
  - 火山模型 SVG：黄色下箭头=next() 调用链
    绿色上箭头=行数据向上流动
  - 每步右侧面板：该工序的输入/输出，一目了然
  - 点击"下一步"/"自动播放"，不用键盘

- **04_wal_and_crash.cpp** ← 迷你 WAL 引擎 + 崩溃恢复（★ 心脏）
  - 重点：WalRecord（40 字节，含 padding 坑，见注释）
  - 提交 = WAL 追加 COMMIT 记录 + fflush + fsync(_commit)
  - 五个场景全实测：
    - 场景2：崩溃 → 重启 → REDO 重放 2 条（页2=1500 页3=800）
    - 场景3：未提交 → 恢复时丢弃 1 条（页4=1000 保持原值）
    - 场景4：torn write（最后 20 字节烂尾）→ 截断；
      有效前缀 2 条（tx5 的 WRITE + COMMIT），REDO 1 条（页5=1234）
    - 场景5：参考机实测随机 159.7ms vs 顺序 157.9ms ≈ 1.0 倍
      （数值随盘和机器变化，结论不变：NVMe 随机≈顺序，fsync 才是大头）
  - 打开时扫 WAL 续 LSN（不是从 1 开始）
  - 结束自动清理 engine.db / engine.wal，不留垃圾

## 四、三道坎（过不去就回头重看）

### 第一坎：两本账的世界观

比较次数（CPU 账）：约 1ns 一次
页读取次数（磁盘账）：约 100μs 一次 = 十万次比较

BNL：2.5 亿次比较 = 0.25 秒 CPU，但 25000 页 = 2.5 秒磁盘
Hash：5.5 万次比较 + 196 页 = 基本可以忽略

这一关所有算法对比，都要分这两个本记，只看一个会得出错误结论。

### 第二坎：优化器的"正确"与"错误"

优化器的算法永远正确——它就是在最小化代价公式。
但代价公式的输入（统计信息）可以错。

STALE 剧本：统计说 amount>100 只有 0.1%，真实有 99%。
优化器"正确地"选了 C（估代价 157.0），
真实代价却是 152710，是正确 A 计划（1072.5）的 142 倍。

修复：ANALYZE。SQLite 的 ANALYZE 填的是 sqlite_stat1 这本账。
别骂引擎，先看看 ANALYZE 跑了没。

### 第三坎：火山模型的"拉"语义

很多人以为数据库是"把整张表读完再过滤"。
火山模型告诉你：不是的。每行都是"要一行给一行"拉出来的。

LIMIT 10 为什么快：不是"扫完再取前 10 行"，
是 Limit 算子拿到 10 行就说 EOF，下层根本不再被调用。

Hash Join 的 BUILD 阶段为什么必须等：
Join.next() 第一次被调用 → 先 while(ScanUsers.next()) 建哈希表
→ 哈希表就绪了 → 才开始向左边要第一行。
这就是火山模型里唯一的"憋大招"时刻。

## 五、八个必踩的坑（都在这关的文件里出现过）

- **坑1**  sizeof(WalRecord) - sizeof(checksum) 不等于校验范围
  → 用 offsetof(WalRecord, checksum)，见 04 的 recChecksum()

- **坑2**  Index NL 在选择率高时爆炸
  → 选择率 > 10% 就用 Hash Join，见 01 的实测数字

- **坑3**  统计过期 → 优化器"正确地"选错计划
  → 跑 ANALYZE，见 02 的三轮剧本

- **坑4**  覆盖索引少了"回表"两个字，代价差出上万次回表
  → 看 EXPLAIN 里有没有 "COVERING INDEX"，见 03 Q1~Q6

- **坑5**  联合索引范围列右边的列全部失效
  → WHERE a=1 AND b>2 AND c=3，c 索引用不上，见 03 Q6

- **坑6**  LIKE 默认大小写不敏感 → 不走索引
  → PRAGMA case_sensitive_like=ON 才行，见 03 Q15

- **坑7**  深分页 LIMIT N,M 要先数过 M+N 行
  → 改写 WHERE id>last_seen LIMIT N，快 84 倍，见 03 Q14

- **坑8**  声明了移动构造就自动没了默认构造
  → MiniEngine() = default 显式补上，见 04 的类定义
