编译命令速查表（PowerShell 直接粘）

# 0) 进入目录
cd database-learning-path/cpp_integration

# 1) 三个连 SQLite 的文件：都要带 -lsqlite3
g++ -std=c++17 -O2 -Wall -Wextra 01_sqlite_c_api.cpp    -o 01.exe -lsqlite3
g++ -std=c++17 -O2 -Wall -Wextra 02_raii_wrapper.cpp    -o 02.exe -lsqlite3
g++ -std=c++17 -O2 -Wall -Wextra 03_thread_pool_db.cpp  -o 03.exe -lsqlite3

# 2) 第四个文件不碰数据库，不需要 -lsqlite3（外部驱动代码在 #ifdef 里）

# 3) 跑
.\01.exe
.\02.exe            # 默认 N=10000，逐条提交那段实测约 119 秒，别当卡死
.\02.exe 500        # 想两秒看完就带个小 N（实测 4.5 秒）
.\03.exe            # 默认 4 线程 × 120 轮 × 每事务 20 条

.\04.exe

文件清单与学习重点

需 -lsqlite3
01_sqlite_c_api.cpp
裸 C API 全流程：open → exec → prepare → bind → step → column → finalize → close。
重点：SQL 注入真的会删表（场景 C 的 admin'; DROP TABLE sessions; -- 把 sessions 表真删了， 后续查询报 no such table: sessions）；对照参数化查询命中 0 行。 另外记死 finalize 不是可选项、errmsg 才是错误现场。
 需 -lsqlite3
02_raii_wrapper.cpp
四个 move-only 的 RAII 类：Db / Stmt / Row / Transaction，配 SqliteError 异常与 [[nodiscard]]。
重点：Row 必须深拷贝（column_text 的指针下次 step 就作废）； 析构不能抛异常，所以 commit 失败必须在 commit() 里抛； 事务是性能第一开关 —— 本机实测逐条 119144.8ms vs 单事务 16.5ms。
 需 -lsqlite3
03_thread_pool_db.cpp
固定大小连接池（mutex + condition_variable + ConnectionGuard RAII 归还）与四种并发策略对照，含 WAL / busy_timeout / 指数退避重试。
重点：busy 必须走返回值，不能走异常（师傅第一版就踩了， 失败 360 次而撞锁计数打印 0）；ROLLBACK 前先把 errmsg 取走； 脏连接归还进池 = 全服写不进去。可配 sqlite3_get_autocommit() 判事务状态。
 不需要 -lsqlite3
04_mysql_and_orm.cpp
MySQL Connector/C++ 与 ODBC 的完整用法写在 #ifdef 里（本机未装，不参与编译）； 编译路径里放的是能跑的编译期列映射和 N+1 / autocommit 成本模型。
重点：网络往返是真数据库的头号成本（所以要池化 + 合并往返）； utf8mb4 不是 utf8；rewriteBatchedStatements 不开，批处理是假的； ORM 的六类逃生场景。本机关未安装 MySQL，外部驱动代码仅作工程参考。
 纯前端
connpool_animator.html
连接池可视化沙盘：M 个连接槽位 + 等待队列 + 请求球，可调池大小 / 到达速率 / 单请求耗时， 三种策略（每次新建 / 无界并发 / 固定池）对比，实时看平均等待、超时数、吞吐。
重点：亲手把池调小，看平均等待怎么涨、超时数怎么起飞的。
 必读
tutorial.md
模块简介、学习目标、学习顺序、七条常见坑、本机实测数据全表、七条课后练习。

参考机实测数据（不是抄来的；你的机器数值会不同，但结论方向一致）

来源测什么实测值结论
02 N=10000逐条自动提交119144.8 ms事务是性能第一开关；单事务比逐条快 7217.4 倍。倍数随机器变，"两三个数量级"到处成立。
02 N=10000单事务批量提交16.5 ms
02 N=10000每 500 条一事务563.0 ms
02建索引耗时26.1 ms建索引比导入 10000 行（14.0ms）还慢 —— 索引不是白送的。
02N+1（50 次单查）vs 一条聚合13.73 / 3.37 ms贵的是往返次数，不是数据量。
03 反面教材busy_timeout=0 不重试失败 360 / 撞锁 360原文 "database is locked"(rc=5)。库里行数 2400 与写入行数一致，证明没写丢。
03每次新建连接1814.8 ms建连 658 次，5290 行/秒；建连阶段的 PRAGMA journal_mode=WAL 本身也会撞锁。
03单连接串行332950 行/秒永远不报错，因为它根本没并发 —— 别把"没报错"当"解决了"。
03连接池 + busy_timeout162774 行/秒480/480 全部成功，建连只 2 次。
03池从 4 压到 2257173 行/秒SQLite 只有一个 writer，池小反而更快。池越大越好是想当然。

04 号文件里的 N+1（86 倍）与 autocommit（3750 倍）是成本模型算出来的，不是实测 —— 本机没有 MySQL。页面上把"实测"和"模型"分开标注，师傅不编数字。

三条最容易被忽略、代价最大的纪律

一、锁冲突是正常事件，不是异常事件。 SQLITE_BUSY / HTTP 429 / RPC deadline exceeded 一律用返回值表达。 用异常表达，你的统计就会说谎 —— 03 号文件里师傅亲眼看见"失败 360 次，撞锁 0 次"。
二、连接还回池子之前必须是干净的。 事务失败必须 ROLLBACK（用 sqlite3_get_autocommit() 判断是否真挂着事务）。 带病连接进池 = 一个线程出错、全服写不进去，而且像随机故障。
三、任何 ORM / 驱动，上线前把它真正发出去的 SQL 看一遍。 MySQL general_log、PG log_statement='all'、SQLite sqlite3_trace_v2。 没看过生成 SQL 就用 ORM，等于闭眼开车。
