（老师傅带徒弟 · 简体中文 · 本机可跑）

## 〇、开工之前，师傅先把环境说死

徒弟啊，这一关跟前几关不一样。前面几关你在 SQL 里打转，这一关你要动手
把数据库"接进"C++ 程序里。接数据库这件事，代码量不大，坑个个要命。

本关只需要两样东西：**一个支持 C++17 的编译器**，和 **SQLite 的开发库**
（头文件 + 链接库）。不需要 CMake，不需要 MySQL/PostgreSQL 服务端。
师傅验证这一关用的环境是这样，你对照着确认自己有没有等价物即可：

```text
g++ (MSYS2 UCRT64)          15.2.0      ← 参考机；MinGW-w64 / Clang 亦可
SQLite 头文件               <prefix>/include/sqlite3.h
SQLite 静态/导入库          <prefix>/lib/libsqlite3.a（或 .so / .dll + .lib）
sqlite3.exe                 3.51.1      ← 用于手工验证 SQL，非编译必需
```

Linux 上一般装 `sqlite3` 开发包即可（Debian/Ubuntu：`libsqlite3-dev`）；
Windows 用 MSYS2 的话是 `pacman -S mingw-w64-ucrt-x86_64-sqlite3`。
链接报 "undefined reference to sqlite3_open"，九成是没加 `-lsqlite3`
或库路径不在搜索目录里。

所以本关的编译命令就一条，抄下来：

```powershell
g++ -std=c++17 -O2 -Wall -Wextra 01_sqlite_c_api.cpp -o 01.exe -lsqlite3
.\01.exe
```

为什么用 SQLite 教"接数据库"？徒弟你可能会撇嘴：SQLite 不就是个单文件小库吗。
师傅告诉你，正因为它是**进程内**的库，你才能把"驱动 API 的形状"
（prepare / bind / step / column / finalize）看清楚，而不被网络、
连接池、服务端调度这些噪音干扰。形状看懂了，换成 MySQL 只是换函数名。
这一点在 04 号文件里师傅会再敲一遍。

## 一、模块简介

这一关一共四个 C++ 文件加两个可视化页面，走的是一条完整的成长线：

- 01  裸 C API：先亲手摸一遍最原始的东西，包括被 SQL 注入打个正着
- 02  RAII 封装：把 C API 包成不会泄漏、不会忘记回滚的 C++ 接口
- 03  连接池 + 并发：把 "database is locked" 抓出来，再治好它
- 04  通向真数据库：MySQL Connector/C++、ODBC、ORM 的能与不能

外加 connpool_animator.html —— 一个连接池的可视化沙盘，你自己调参数
看平均等待时间、超时数、吞吐怎么变。有些直觉，跑十遍动画比看十页书管用。

这一关的定位不是"教你用某个库"，是让你建立三个肌肉记忆：

- 一，参数化查询是默认，拼字符串是例外（而且这个例外基本不该存在）；
- 二，资源交给对象管，收尾是编译器的事，不是你的事；
- 三，事务粒度是数据库性能的**第一**开关，不是索引，不是缓存。

## 二、学习目标

学完这一关，你应该能做到：

1. 不用任何文档，徒手写出 open → exec → prepare → bind → step → column →
   finalize → close 这条流水线，并说清每一步忘了会出什么事。
2. 亲手复现一次 SQL 注入（本关 01 号文件里那个 DROP TABLE 是真删掉了），
   并且能解释**为什么**参数化能根治它，而不是"加个转义函数"。
3. 用 C++17 写一个 move-only 的连接/语句封装，让"双重释放"和
   "忘记 finalize"从运行时 bug 降级成编译错误。
4. 说清析构函数为什么不能抛异常，以及"提交失败"该在哪一层抛给上层。
5. 拿到实测数据说服你的同事：逐条提交和单事务提交差了三个数量级左右
   （参考机上约 7200 倍；你机器上倍数会不同，但"两三个数量级"到处成立）。
6. 处理 SQLITE_BUSY：知道 WAL、busy_timeout、应用层重试这三板斧的
   先后顺序和各自适用的场景，并能读懂 busy handler 的返回值语义。
7. 判断一个 C++ 项目该不该上 ORM，以及热路径该在什么时候退回裸 SQL。

## 五、常见坑 —— 全是师傅自己或身边人踩过的

1. sqlite3_finalize 不是"可选项"。
   症状：程序退出时 sqlite3_close 返回 SQLITE_BUSY，连接关不掉，
   或者内存缓慢增长。SQLite 的语句对象是挂在连接上的资源，
   你不 finalize 它就一直占着读锁。01 号文件里师傅专门写了"不 finalize
   会怎样"的注释。C++ 里这件事交给 Stmt 的析构，这就是 02 存在的理由。

2. sqlite3_column_text 返回的指针属于语句。
   症状：单步调试时值是对的，存进 vector 之后再打印全是乱码或者最后一行。
   原因：那个 const unsigned char* 指向语句内部的缓冲区，下一次
   sqlite3_step 就把它复用了。02 号文件里的 Row 在构造时就把所有列
   深拷贝走，所以 Row 可以安全地离开语句单独存在。
   记住这句：**你看到的指针不是你的，值才是你的。**

3. 【本关最贵的一条】busy 不能用异常表达。
   师傅在写 03 号文件的时候，第一版是这样写的：

   ```cpp
   try { conn.exec("BEGIN IMMEDIATE"); ... }
   catch (...) { other_errors++; }
   ```

   跑出来的结果是：480 个事务失败了 360 个，而"撞锁次数"打印出来是 **0**。
   我当时以为并发调度太顺没冲突，盯着屏幕半天想不明白"失败了 360 次，
   BUSY 怎么会是 0"。根因是：BEGIN IMMEDIATE 抢不到写锁时返回 SQLITE_BUSY，
   而 exec() 把它当成错误抛了异常，于是全部落进 catch(...) 被归成
   "其他错误"。分类统计彻底说谎。
   改成 try_exec() 返回 rc 之后，同一个程序立刻打印出
   "撞锁 360 次，原文 database is locked"。
   教训写成长一条：**在并发场景里，锁冲突是正常事件，不是异常事件。
   正常事件用返回值表达，异常只留给真正意外的事情。**
   这条规律不限于 SQLite：MQ 的"消息暂时不可用"、HTTP 的 429、
   RPC 的 deadline exceeded，全都是一个道理。

4. ROLLBACK 之前先把 errmsg 取走。
   03 号文件里另一个自己踩的坑：抓"撞锁原文"时先执行了 ROLLBACK，
   结果打印出来的是 "cannot rollback - no transaction is active"，
   因为 errmsg 是连接上的**单一槽位**，会被最后一次调用覆盖。
   顺手还学会了一个 API：sqlite3_get_autocommit()，返回 0 才说明
   当前真挂着事务，才需要 ROLLBACK。判断状态要问权威 API，别自己记标志位。

5. 事务失败不 ROLLBACK，会让整条连接变成"带病连接"。
   连接池场景下这是灾难：一个线程出错，把挂着半个事务的连接还回池子，
   下一个拿到它的人写什么都是 "database is locked"，
   而且现象会像"随机发作的线上故障"，极难定位。
   规矩：**归还连接到池之前，必须保证它是干净的**（RAII 的
   Transaction 析构 + ConnectionGuard 归还前检查，双保险）。

6. MySQL 的 utf8 不是 utf8。
   它是 3 字节的残缺实现，四字节字符（emoji、部分生僻字）直接报
   "Incorrect string value"。新建库一律 utf8mb4 + utf8mb4_0900_ai_ci。
   这条不属于 C++，但每年害死的人比前面几条加起来还多。

7. ORM 的批处理可能是假的。
   Connector/C++ 里你老老实实写了 addBatch/executeBatch，
   连接串没开 rewriteBatchedStatements=true，驱动照样一条条发。
   所以"优化没效果"的时候，先看驱动日志里真正发出去的语句长什么样。
   师傅的规矩：**任何 ORM/驱动，上线前把生成的 SQL 打开看一遍。**

## 六、经验之谈 —— 数据摆在这儿，你自己看

下面是参考机（g++ 15.2 + SQLite 3.51.1 + UCRT64）的输出，
没有任何一个数字是编的。你跑出来会不一样，别抄数字，抄结论。

### 02 号文件 · N = 10000 条 INSERT（实测）

```text
    场景1 逐条自动提交        119144.8 ms   （平均每条 11.914 ms）
    场景2 单事务批量提交           16.5 ms   （平均每条 0.002 ms）
    场景3 每 500 条一个事务       563.0 ms

    >>> 单事务比逐条快 7217.4 倍；每 500 条一批比逐条快 211.6 倍。
```

平均每条 11.9 ms 是什么概念？那就是一次 fsync 的成本。
逐条提交 = 每条一次 fsync + 一次日志写入。磁盘快慢、有没有杀软、
系统缓存状态都会改变这个倍数，所以倍数别背，结论要背：
事务是性能第一开关。索引是第二开关。其他都是第三档。

那为什么不干脆全放一个事务？因为长事务会：

- 失败时代价是整批重做；
- 挡住 WAL checkpoint，WAL 文件越撑越大；
- 别人在快照隔离下读到的仍是旧快照（不是被阻塞，而是看到"过时但一致"的数据）。

500~5000 条一批是常见起手值，然后拿真实负载压测再定。

同一份输出里的其他实测：

```text
    导入 10000 行（批量事务） 14.0 ms
    建索引 idx_orders_user    26.1 ms   ← 索引不是免费的，写放大就在这
    有索引比无索引快           2.0 倍
    N+1 循环单查 50 次        13.73 ms
    改成一条聚合查询           3.37 ms
```

注意"建索引 26.1ms 比导入 14ms 还慢"这件事 —— 很多人以为索引是白送的。

### 03 号文件 · 4 线程 × 120 轮 × 每事务 20 条 = 9600 行（实测）

```text
    反面教材（busy_timeout=0，不重试）
        18.1 ms │ 成功事务 120/480 │ 失败 360 │ 撞锁 360 次
        打印原文："database is locked"（rc=5）
    单连接串行
        28.8 ms │ 9600 行 │ 332950 行/秒 │ BUSY 0
    每次新建连接
      1814.8 ms │ 成功 480 │ 建连 658 次 │ 5290 行/秒
        （658 > 480 是因为失败也建了连接；而且建连阶段的
          PRAGMA journal_mode=WAL 本身也会报 "database is locked"）
    连接池 + busy_timeout=5000ms
        59.0 ms │ 480/480 │ 撞锁 1 │ 162774 行/秒 │ 建连 2 次
    连接池 + 应用层重试
        48.4 ms │ 480/480 │ 撞锁 2 │ 198341 行/秒 │ 建连 2 次
    池大小压到 2（线程仍是 4）
        37.3 ms │ 480/480 │ 1 次重试 │ 257173 行/秒
```

三个必须带走的结论：

① 连接池的价值不在"快一点"，在于把建连成本从 O(请求数) 降到 O(池大小)。
   真数据库建一条连接是 TCP+TLS+认证，5~50ms，不池化 QPS 上限就是它的倒数。

② "单连接串行"永远不报错，因为它根本没并发。
   别把"没报错"当成"解决了"，那是掩盖。

③ SQLite 只有一个 writer，所以池从 4 压到 2 吞吐反而更高。
   换成 OLTP 类真数据库也一样：连接数超过"能同时干活的核数"之后，
   排队、上下文切换、锁竞争的代价会吃掉并发收益，吞吐不再上升甚至下降。
   I/O 密集的库能容纳更多连接，但最终也会撞到同一堵墙。
   "池越大越好"是想当然，你手里的数据说：2 就够了。

### 04 号文件 · 成本模型（不连库也能算的账）

```text
    N+1：200 个子记录 × 每个 5 行，同机房 MySQL 往返 300us
        lazy loading  60 ms
        一条 JOIN      1 ms   → 86 倍
    autocommit 税：N=10000，E=1.5us，fsync F=9000us
        每条一个事务  90015 ms
        包成一个事务     24 ms  → 3750 倍
```

这两个数字是模型算的（本机没有 MySQL），但它们和上面 SQLite 的实测
讲的是同一件事：**贵的是往返次数和落盘次数，不是数据量。**

## 七、课后练习（做完再进第五关）

### 练习 2（必做，40 分钟）

把 02 号文件的 Transaction 改成支持嵌套（savepoint）。
接口：外层 BEGIN，内层 SAVEPOINT sp1，内层失败只 RELEASE/ROLLBACK TO sp1，

做完你会真正理解 SQLite/MySQL 对嵌套事务的原生态度（都不支持，
都得靠 savepoint 模拟）。

### 练习 3（必做，20 分钟）

故意把 02 的 Row 改成"只存 sqlite3_column_text 的指针不拷贝"，

### 练习 4（必做，45 分钟）

### 练习 5（进阶，1 小时）

给 03 的连接池加两样生产必备的东西：

  b) 平均/P99 等待时间的统计输出。
然后把线程数调到 16、池调到 2，看等连接超时数字起飞，
再回答：这时应该扩池还是缩短事务？依据是什么？

### 练习 6（选做，1 小时）

### 练习 7（选做，读代码）

让 order_placeholders() 自动变成 5 个问号。

做完这七条，你就可以进第五关（结丹期）看查询内幕了。
到第 7 关手搓迷你数据库时你会发现，这一关写的每一个 RAII 封装，
都是在给"数据库内部本来就该有的东西"打草稿。
