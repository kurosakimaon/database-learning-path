策略对应同目录代码排队行为它到底在赌什么
① 每请求新建连接03_thread_pool_db.cpp 的反面教材档 不排队，因为没有限流；N 个请求就开 N 条连接 赌"建连很便宜"。同一份代码跑下来，这一档的建连次数 ≈ 请求数（数量级 10³）， 而池化那几档只有池大小那么几条；耗时随之高出一个数量级，还要顺手撞一堆 database is locked。 具体毫秒数每台机器都不同（盘、CPU、是否本地库都会改它），别背数字， 要背的是那个倍数关系：O(请求数) 次握手 ÷ O(池大小) 次握手 —— 赌输了
② 小池 + 无限排队ConnectionPool::acquire 不设超时 队尾无限延长，谁都不得罪，只是全都慢 赌"请求总会排到"。过载时等待时间无上限，上游先超时，然后重试，队伍更长 —— 雪崩的标准开场
③ 小池 + 有界队列 + 超时acquire(..., timeout) + 队列上限 队列满了直接拒；排队超过阈值直接放弃，不再占队列位（已经拿到连接的那条照常跑完再归还） 赌"宁可快速失败，也不要全体慢死"。这是生产环境唯一活下来的写法

师傅的四条硬规则

# 1. 先算 M* = λ × S。这是稳态下同时"活着"的请求数，也就是连接池的理论最小规模
#    λ = 45 req/s，S = 30 ms  →  M* = 45 × 0.030 = 1.35 → 池给 2~3 条就够
#    λ = 120 req/s，S = 90 ms →  M* = 120 × 0.090 = 10.8 → 给 3 条池？那就是策略②的灾难现场
#    （这条是 Little 定律：稳态下 L = λW，与到达过程是不是泊松无关 —— 所以它好算也好用）

# 2. 池大小不是越大越好。超过 DB 服务器能真正并行处理的量之后，
#    多出来的连接只在数据库内部排队，你还白白多付一份连接内存和握手时间。
#    PostgreSQL 更狠：一条连接 = 一个后端进程（默认 shared_buffers 摊薄 + 每进程约 10MB），
#    池开到 200 就是 200 个进程在抢 CPU 和缓冲区，吞吐反而掉。
#    SQLite 更绝：写者只能有一个，池开到 64 条，第 2~64 个写者全在撞 "database is locked"
#    （WAL 模式让"读"不再被写挡住，但写者之间依然只有一个，busy_timeout 只是让你多等一会儿）。

# 3. 一定要有超时和上限，并且超时值要小于上游给你的预算。
#    上游网关 500ms 超时，你排队 600ms 才拿到连接 —— 上游早就断开重试了，
#    你却还在给一个没人要的请求干活，同时把连接占住。

# 4. 池里的连接是会老的，别把它当永久资源。
#    服务端会单方面关掉空闲连接（MySQL 的 wait_timeout 默认 8 小时、PgBouncer/云代理
#    常常几分钟），中间层的空闲断连更常见。你这边还留着一条"看起来能用"的连接，
#    下一次用它就是 broken pipe / MySQL 2006 "MySQL server has gone away"。
#    所以生产池必须配齐三样：maxLifetime（设得比服务端超时更短）、借出时的有效性检查
#    （ping / validationQuery）、空闲驱逐。HikariCP 默认 maxLifetime=30 分钟就是在替你做这件事。
#    注意"检查"本身也要花钱：每条都 ping 一次等于把开销还回来了，所以只借出时查、
#    或按时间阈值查，别在归还时查。
