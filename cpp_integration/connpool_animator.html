策略对应本机代码排队行为它到底在赌什么
① 每请求新建连接03_thread_pool_db.cpp 的反面教材档 不排队，因为没有限流；N 个请求就开 N 条连接 赌"建连很便宜"。本机实测：120 轮建连 658 次、1814.8 ms，还撞了 360 次锁 —— 赌输了
② 小池 + 无限排队ConnectionPool::acquire 不设超时 队尾无限延长，谁都不得罪，只是全都慢 赌"请求总会排到"。过载时等待时间无上限，上游先超时，然后重试，队伍更长 —— 雪崩的标准开场
③ 小池 + 有界队列 + 超时acquire(..., timeout) + 队列上限 队列满了直接拒；排队超过阈值直接放弃并归还连接 赌"宁可快速失败，也不要全体慢死"。这是生产环境唯一活下来的写法

师傅的三条硬规则

# 1. 先算 M* = λ × S。这是稳态下同时"活着"的请求数，也就是连接池的理论最小规模
#    λ = 45 req/s，S = 30 ms  →  M* = 45 × 0.030 = 1.35 → 池给 2~3 条就够
#    λ = 120 req/s，S = 90 ms →  M* = 120 × 0.090 = 10.8 → 给 3 条池？那就是策略②的灾难现场

# 2. 池大小不是越大越好。超过 DB 服务器能真正并行处理的量之后，
#    多出来的连接只在数据库内部排队，你还白白多付一份连接内存和握手时间。
#    SQLite 更绝：写者只能有一个，池开到 64 条，第 2~64 个写者全在撞 "database is locked"。

# 3. 一定要有超时和上限，并且超时值要小于上游给你的预算。
#    上游网关 500ms 超时，你排队 600ms 才拿到连接 —— 上游早就断开重试了，
#    你却还在给一个没人要的请求干活，同时把连接占住。
