# 第 2 关：炼气期 · 存储与索引

老师傅带你钻到数据库肚子底下看一圈

## 一、模块简介

徒弟啊，上一关你把 SQL 写顺手了。
这一关师傅要带你干件"过分"的事：
把数据库掀开，看看 SQL 底下到底发生了什么。

先记住一句话，这一关反复说、天天说，说到你烦为止：

> ◆ 数据库的一切设计，都源于这对矛盾：
>   磁盘按页读写，内存断电即失。◆

拆开讲：
  磁盘那边——你不能"读一个 int"。磁盘的最小读写单位是页
  （数据库里一般 4KB、8KB 一页）。你要 1 个字节，它也得
  把整页 4096 字节搬给你；随机读一次约 100 微秒，
  顺序读的带宽是随机读的几十倍。
  内存这边——快，1 纳秒量级，比磁盘快十万倍。
  但它是"断电即失"的：进程崩了、机器重启了，全没了。

快但记不住的是内存，记得住但慢得离谱的是磁盘。
数据库的全部工作，就是在这俩之间做搬运和记账：
  Buffer Pool —— 在内存里扣一块，缓存磁盘页，对抗"慢"；
  WAL 日志 —— 改东西先顺序追加写日志，对抗"断电即失"；
  B+ 树 —— 把"找一页"的随机 I/O 次数压到树高，对抗"按页读写"；
  页内槽目录 —— 定长页里装变长记录，还是对抗"按页读写"。

你看，没有一样发明是凭空来的，全是被这对矛盾逼出来的。
这一关你就带着"这玩意儿是怎么被逼出来的"这一条线走，
所有的设计突然就讲道理了。

你是写 C++ 的，师傅给你几个翻译：
  页（page） ≈ 一块定长的 mmap 区域，偏移量就是"指针"；
  Buffer Pool ≈ 带淘汰策略的对象池（你写过 LRU 缓存吧）；
  B+ 树节点 ≈ 一个定长结构体，里面是 key 数组 + 孩子页号；
  页号代替指针 ≈ 把 std::vector 的下标存进文件——
                内存地址断电就没，页号永远有效。

本关所有示例都用 C++ 手写，不用任何数据库，
你要的就是"亲手造一个小的，再看真的大的"。

## 二、学习目标

学完本模块，你要能做到：

1. 说清"页"的账：读 1 个 int 为什么是 4096 字节的 I/O，
   I/O 放大是什么，为什么数据库程序员张口闭口都是页
2. 手写一个槽式页（slotted page）：定长页里怎么装变长记录，
   为什么页内存偏移而不是存指针
3. 手写 Buffer Pool：LRU 淘汰、脏页写回、pin 住不能踢，
   能拿命中率算账，知道全表扫描为什么能"洗掉"热数据
4. 手写 B+ 树（阶 4 到阶 101），讲清四件事：
   为什么扇出大 → 树就矮 → I/O 就少；
   为什么叶子存数据、内部只存路标；
   为什么叶子要串成链表；
   分裂时 key 什么时候复制上提、什么时候上提不留
5. 用数字回答"为什么不用红黑树/二分/哈希"：
   比较次数是 CPU 的账，页读取次数才是磁盘的账，
   两本账要分开算——只看比较次数会得出完全错误的结论
6. 在真 SQLite 上验证索引：EXPLAIN QUERY PLAN 里
   SCAN 和 SEARCH USING INDEX 的天壤之别；
   覆盖索引为什么快；联合索引最左前缀；
   五种让索引失效的常见写法，以及每一种背后的道理
7. 建立"优化器是个会计"的观念：它不认"快不快"，
   只认估算的行数和代价公式——所以统计信息错了它就选错计划

**02_btree_vs_sorted_array.cpp** ← 100 万数据的四方案大对决（★ 本关心脏）
  重点：同一批 100 万个 int，摆四种方案同台比价：
  A 无序数组线性扫 / B 有序数组二分 / C 手写 B+ 树 / D 红黑树。
  程序把"比较次数"和"页读取次数"分两栏记账，
  你会亲眼看到：D 红黑树比较 18 次比 C 的 25 次还少，
  但页读取 D 要 18 次、C 只要 4 次——账一换本，结论翻转。
  再看程序里那棵真实生长的 B+ 树：100 万 key，
  树高 4 层、14610 个节点、内部节点平均填充率 58%——
  理论 3 层装得下，实际多长一层，因为分裂只填六成。
  范围查询那一段是全文件最值钱的一屏：
  B+ 树顺叶子链表 150 页搞定，逐个点查要 40004 页，266 倍。
  最后现场测"顺序访问 vs 随机访问 400 万个 int"（参考机约 5~8 倍差，
  随 CPU 缓存和机器波动），这就是 CPU 缓存行给你的"按页读写"体验卡。
  编译：

```powershell
g++ -std=c++17 -O2 02_btree_vs_sorted_array.cpp -o 02
```

**03_index_in_practice.sql** ← 真 SQLite 上的索引实验（★ 落地验证）
  重点：WITH RECURSIVE 现场造 20 万行订单 + 5000 行用户，
  22 处 EXPLAIN QUERY PLAN，每处都把真实输出注释在语句旁边，
  你跑一遍就能对答案。六节内容层层递进：
    无索引 SCAN → 建索引 SEARCH，同一句话两种命；
    聚簇（INTEGER PRIMARY KEY，表就是树）vs 二级索引（存 rowid，要回表）；
    覆盖索引：SCAN ... USING COVERING INDEX，压根不碰主表；
    联合索引最左前缀：跳过第一列，第三列直接作废；
    五种失效写法：对列做函数、隐式类型转换（phone+0）、
      前导通配 LIKE、OR 拆碎、低选择性列优化器主动放弃。
  每条语句后面都有 "-- 要点："，先猜计划再看注释。
  跑法：

```powershell
sqlite3 :memory: ".read 03_index_in_practice.sql"
```

**btree_animator.html** ← B+ 树插入 / 查找动画（★ 本关最重要的教具）
  重点：阶 = 4，每个节点最多 3 个 key，满了就分裂。
  「插入」输数字、「查找」查一个点、「范围查」输 `20~45`、
  「插入随机」（撞过重复键会被主键约束挡掉，理由写在解说里）、
  「自动演示」连插 12 个数——分裂、上提、长高一场看全；
  「撤销」回到上一次插入前的快照，「重置」清空。
  右侧三个计数器就是本关的世界观（前两个显示"本次操作"的账单，空闲时归零）：
    比较次数（CPU 的账，页内二分最坏 ⌈log₂(n+1)⌉ 次）；
    页读取次数（磁盘的账：<b>纯查找永远等于树高</b>，
      未命中也一样贵；插入额外要付分裂那几页的<b>写</b>）；
    树高。
  盯着分裂那两帧：叶子分裂，右半最小的 key 是"复制"上提
  （数据必须留在叶子里）；内部节点分裂，中间 key 上提后
  "自己不留"（路标只能有一份）。这两条规则文字看十遍，
  不如动画看一遍。叶子间的虚线箭头是链表，范围扫描的命根子：
  「范围查」会让你看清 读页 = 下降几页 + 横向几页。

**bufferpool_animator.html** ← Buffer Pool 动画（LRU vs Clock vs 中点插入）
  重点：8 帧内存池 + 20 页磁盘文件。
  「访问页 N」手动敲（35% 概率把页改脏）；
  「播放自动序列」= 热点访问 → 冷数据冲刷 → 回访热点；
  「制造缓存污染」= 先热身再全表扫 20 页再回访热页
    （空池直接扫是看不出污染的——池里本来就没热页可挤），
    亲眼看热页怎么被扫描数据洗出去、命中率怎么砸下来。
  「三种策略跑同一条扫描」= 把同一条 40 次访问的序列给三个
    算法各跑一遍，右侧三格一次填齐，不用手点三次。
    本机实测：LRU 40.0%（淘汰 16）＝ Clock 40.0%（淘汰 16）
    ＜ 中点插入 50.0%（淘汰 12），扫描后再回访的 12 次热点
    命中 8/12、8/12、12/12 —— 中点插入那 12 次全数命中，
    热页一页没被扫描冲掉。
  顶部三个 tab：LRU / Clock（二次机会）/ 中点插入。
  盯三个细节：脏页被踢之前必有一次"帧 ──写回──▶ 磁盘"；
  LRU 命中要把帧提到队首（真实引擎里这要拿 latch），
  Clock 命中只把一个 bit 置 1——这是操作系统爱用
  Clock 系算法的原因。<b>但别把 Clock 当防污染的药</b>：
  它省的是链表 latch，命中率只是近似 LRU，同一条扫描序列上
  两者分数一模一样，热页照样被洗光。
  InnoDB 用的是另一招（改进 LRU = midpoint insertion）：链表前
  5/8 是年轻区、后 3/8 是老区（innodb_old_blocks_pct=37），
  新页插到交界点而不是队首，老区页要待满
  innodb_old_blocks_time（默认 1000ms）后再被访问才晋升队首，
  淘汰只从队尾（老区尾部）下手——扫描带来的垃圾页因此只在
  老区里自相残杀，热页住在年轻区不动。PostgreSQL 走的是
  另一条路：大表顺序读直接进 ring buffer，不进主缓存。

## 四、学习建议与常见坑

师傅给你划三道坎，再列一串坑。

### 第一道坎：两本账（02 的主线）

CPU 的账：比较次数。纳秒级，做十亿次才一秒钟。
磁盘的账：页读取次数。一次随机 I/O 约 100 微秒 = 十万次比较。
所以任何"比较次数少"的方案，只要页读次数多，都是花架子。
以后你看任何数据结构、任何执行计划，先问一句：
"这玩意儿读几页？"——这一问能避开 80% 的性能坑。

### 第二道坎：B+ 树分裂的三条规则（配 btree_animator.html）

1. 只有叶子装真正的数据；内部节点只存"路标"（分隔 key + 孩子页号），
   所以一页能塞一百多个分叉 → 扇出大 → 树矮 → I/O 少。
2. 叶子满了一分为二，右半最小的 key【复制】一份上提给父亲，
   自己留着——叶子层的 key 是数据本体，一份都不能少。
3. 内部节点满了也一分为二，中间 key 上提后【自己不留】——
   路标只能有一份，留两份路由就错了。
4. 根分裂时新建一个根，树长高一层；除了分裂没有别的长高方式。

在动画里插到第 8 个数左右就会撞见连环分裂 + 长高，慢慢放慢速看。

### 第三道坎：最左前缀（03 的第 4 节）

联合索引 (a, b, c) 是一棵按 (a,b,c) 整体排序的树。
给了 a 才能定树的位置；只给 b、c，整棵树里 b 是散的，白搭。
所以 (a,b,c) 能服务 a / a,b / a,b,c 三种查询，
"b,c" 服务不了——但"覆盖索引"有豁免权：
数据全在索引页里时，优化器宁可全扫一棵窄树（03 里
"SCAN orders USING COVERING INDEX"那行就是它）。

### 学习方法（跟学 C++ 一模一样）

1. 01、02 先通读代码再看输出——这次反过来，代码是你的母语；
2. 跑起来，逐屏对数字：树高、命中率、I/O 次数，猜一个再看真的；
3. 改参数：02 里把每页 key 数从 100 改成 4 试试（扇出砍到 5，
   看树高从 4 变几）；03 里把某条 WHERE 的写法改"对"，
   看计划从 SCAN 变 SEARCH；
4. 动画玩出感觉后，合上文件，拿纸手画阶 4 插入 8 个数，
   画对了这一关就算通了。

### 常见坑（每一条师傅都踩过）

1. **【拿 vector 引用又 push_back】**
   02 初版就栽了：split 里攥着 BPlusNode& 又去 new_node()，
   nodes_ 一扩容引用全体悬垂，std::bad_alloc 当场暴毙。
   凡"持引用期间容器可能扩容"，一律改用下标重新索引。
   （这个坑师傅真踩过，就埋在本关代码的历史里。）

2. **【页内偏移不是指针】**
   页里存"记录到页心的偏移"，不存地址。地址是进程这辈子的临时工，
   页号+偏移才是数据库户口本上的正式名字。写 01 时想明白这条，
   后面 WAL、复制、备份全通。

3. **【LRU 命中率不是越高越好地看】**
   冷数据全表扫描会把热页踢光（buffer pool 污染）。
   动画里点「制造缓存污染」看热页死亡回放。
   注意<b>二次机会（Clock）救不了这一枪</b>：同一条序列上它和
   LRU 实测同分（40.0% vs 40.0%），它省的是"命中必改链表"的
   latch，不是命中率。InnoDB 的解法是链表 5/8 处插入 +
   老区待满 1 秒才转正——新页先"观察"，撑过冷区才有资格进热区。
   （所以背算法别背名字，要看它防的是哪一种代价。）

4. **【淘汰不贵，淘汰脏页才贵】**
   干净页和磁盘一模一样，直接覆盖，0 次 I/O；
   脏页必须先写回。所以 Buffer Pool 省了读、欠了写，
   数据库的写放大、检查点（checkpoint）全是从这笔账长出来的。

5. **【EXPLAIN 输出的表示法各家不同】**
   SQLite 里"回表"不单独成行，一行 "SEARCH ... USING INDEX" 就完了；
   MySQL 会拆成两行（index + table）。别拿一家的图背另一家的题。

6. **【LIKE 的大小写陷阱（SQLite 特有）】**
   SQLite 的 LIKE 默认对 ASCII 大小写不敏感，因此【不走索引】，
   哪怕写 'abc%'。得 `PRAGMA case_sensitive_like = ON` 才走。
   03 的 5.3 节专门演了这一幕。

7. **【索引不是越多越好】**
   每加一棵树，每次 INSERT/UPDATE 就多写一棵。
   03 第 4 节里师傅先 DROP 掉两棵小树才演示最左前缀——
   不然优化器会被"互相抢活"的索引搅浑，你根本看不清计划。

8. **【低选择性列，优化器会主动弃用索引】**
   status 只有 4 种值，命中的是四分之一的行（5 万行），走索引 = 多一倍随机回表，
   会计一算就放弃。这不是 bug，是它算对了。
